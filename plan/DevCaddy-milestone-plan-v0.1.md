# DevCaddy 开发阶段与里程碑计划

> 版本：v0.1（2026-11-14）  
> 状态：执行建议稿；按个人空闲时间迭代，不预设日历交付日期。  
> 配套文档：《DevCaddy 个人开发需求清单》。

## 1. 计划目标与使用方法

本文件回答**“按什么顺序做、每一步交付什么、怎样演示或验收”**。需求的定义和范围以配套需求清单中的编号为准。

采用 **功能优先、工程能力渐进完善** 的路线：

1. 先有可启动的最小应用与最小模块边界。
2. 每次完成一个真正能自用的工具，尽快形成使用反馈。
3. 自动化测试从第一阶段保留最低基线，完整测试体系与 CI 后期集中强化。
4. Windows 优先交付；平台依赖早期隔离，Linux 真实移植后期实施。
5. 不为 CMake 语法覆盖或“完美微内核”引入没有实际用途的复杂度。

**AI 与作者分工**：作者自己编写与调试 C++/CMake；AI 参与需求拆解、设计选项、测试案例、审查和问题分析。每个里程碑应尽量独立运行、独立验收。

## 2. 统一的里程碑完成定义（DoD）

里程碑与普通任务的区别：里程碑应形成**可构建、可运行、可演示或可客观验证的结果**，不能仅仅是“写完某个类”。

除个别纯工程验证里程碑外，每个里程碑完成时应满足：

- [ ] 按当前 Windows 构建方式完成构建，生成可运行产物；不能依赖上一次构建残留的偶然状态。
- [ ] 按文档完成规定的演示场景，结果与预期一致。
- [ ] 当前功能的最少关键测试通过；出现新错误时有可理解的提示。
- [ ] 之前已完成的核心能力没有明显回归（执行相关快速测试和最简人工冒烟）。
- [ ] 在 Git 中记录完成状态、提交、已知限制与必要的使用说明。

**测试策略**：每个功能里程碑至少有“正常用例 + 边界/错误用例”的最低自动化验证；M08 才集中扩充完整测试矩阵、CI 和必要的集成测试。这样既减少前期成本，也为后期重构留下安全网。

**阶段门策略**：只有对验收构成实际阻碍的问题需要在本里程碑解决；外观优化、额外格式和非关键工程增强进入后续待办。遇到边界设计确实不合理时允许调整后续里程碑，但保留已交付的可运行状态。

## 3. 阶段总览

| 阶段 | 里程碑 | 阶段核心目标 | 阶段结束时的可见成果 |
| --- | --- | --- | --- |
| A 最小可运行应用 | M00 | CMake、GUI、日志、工具注册最小闭环 | 能启动、切换工具、查看日志的 Windows 程序 |
| B 核心工具功能 | M01–M06 | 六个工具按使用价值逐步实现 | 六个可独立使用的工具 |
| C 工程化交付 | M07–M10 | 国际化/配置、回归测试/CI、安装包、发布 | 可测试、可安装、可从 GitHub 获取的 Windows 版本 |
| D 跨平台验证 | M11–M12 | Linux 核心构建与 GUI 移植 | Linux 可构建、可运行通用工具的版本 |

里程碑编号是追踪用标识，不代表每项工作必须耗时相同。M01–M06 可以根据实际急需程度调整顺序，但每项仍应独立验收。

## 4. A 阶段：最小可运行应用

### M00 — 打通 CMake、Dear ImGui 与最小工具壳

- **目标**：证明工程可以稳定构建、启动、展示窗口，并能容纳新增工具。
- **开发内容**：创建 Git 仓库和 CMake 目标；接入 SDL3 + Dear ImGui（拟采用 OpenGL3）；实现主窗口、工具导航、日志窗口与一个占位工具；创建最简工具注册接口；接入 `include(CTest)` 和一项可运行的测试；提前处理中文字体/源码 UTF-8 基础问题。
- **产出**：Windows 可执行程序、最小源码目录结构、基础构建说明、初始测试目标。
- **演示**：运行程序，在工具导航中打开占位页；按钮触发一条消息并在日志窗口出现；关闭和重启应用；执行 CTest 显示测试成功。
- **验收**：① Debug/Release 至少在主力 Windows 环境可编译；② 正常启动和退出；③ 工具注册后能显示对应页面；④ 日志窗口可用；⑤ 至少一项测试可由命令行执行。
- **不做**：真正功能算法、动态 DLL 插件、多平台打包、复杂全局事件总线。
- **依赖**：无。关联需求：SHELL-01/02、SHELL-03 基础、ENG-01/02 基础。

## 5. B 阶段：核心工具功能

### M01 — JSON 工具成为第一个可自用模块

- **目标**：完成一次“算法与 GUI 分离、工具注册、测试、实际使用”的完整纵向切片。
- **开发内容**：独立 JSON 逻辑库与 ImGui 页面；输入、格式化、单行化、复制、错误提示；少量有效/无效 JSON 测试。
- **产出**：可独立打开并日常使用的 JSON 工具。
- **演示**：粘贴多行 JSON → 一键单行化 → 复制；再格式化为多行；输入非法尾逗号并显示错误。
- **验收**：① 合法 JSON 双向操作正确且语义不变；② 无效 JSON 不输出伪成功结果；③ 纯逻辑测试无需 GUI 可运行；④ 不影响 M00 的导航和日志。
- **不做**：JSON↔YAML/XML、Schema、完整 JSON 编辑器。
- **依赖**：M00。关联需求：FUN-01、SHELL-02。

### M02 — 字符串编码结果展示可用

- **目标**：针对实际字符串编码问题给出可复制的不同编码字节结果。
- **开发内容**：输入框、编码结果表、UTF-8/UTF-16LE/UTF-16BE 及约定的 GBK/GB18030 转换、复制与错误处理；测试中英文与不可编码字符。
- **产出**：字符编码工具。
- **演示**：输入 `中` → 比较 UTF-8 `E4 B8 AD`、UTF-16LE `2D 4E`、UTF-16BE `4E 2D`、GBK `D6 D0`；复制其中一种结果。
- **验收**：① 已约定编码的结果符合样例；② 中文/英文/特殊字符不乱码；③ 无法表示的字符得到明确失败反馈；④ 核心转换不依赖 GUI。
- **不做**：识别粘贴字符串的原始编码、复杂批量转换。
- **依赖**：M00；建议在 M01 后沿用模块模式。关联需求：FUN-02。

### M03 — UUID 生成器可用

- **目标**：可以快速生成并复制标准 UUID。
- **开发内容**：UUID v4 算法/库、单个与批量生成、结果列表和复制；格式与版本字段测试。
- **产出**：UUID 工具。
- **演示**：生成一个 UUID 并复制；批量生成 10 个并检查数量与格式。
- **验收**：① UUID v4 格式、版本位和变体位符合要求；② 批量数量准确；③ 运行失败时不显示伪造成功结果。
- **不做**：v7、排序、数据库 ID 管理。
- **依赖**：M00。关联需求：FUN-03。

### M04 — 哈希摘要工具可用

- **目标**：能够可靠计算开发中常见的文本/文件摘要。
- **开发内容**：SHA-256、可选 MD5；文本默认按 UTF-8 转字节；复制结果；如纳入文件摘要，采用分块读取并处理失败路径；标准向量测试。
- **产出**：哈希工具。
- **演示**：输入 `abc`，计算 SHA-256 并对照已知向量；选择文件（如果该功能已纳入）计算并与外部校验工具对照。
- **验收**：① 已支持算法与权威测试向量一致；② 文本编码规则明确；③ 错误可诊断；④ 文件处理不一次性无限量载入内存。
- **不做**：密码保存、加密解密、签名、证书管理。大文件卡顿问题若真实出现再决定 Asio 的引入时点。
- **依赖**：M00。关联需求：FUN-04。

### M05 — 文件编码检测可用

- **目标**：对真实文件提供合理、可解释的可能编码判断。
- **开发内容**：只读文件选择、BOM/UTF-8 检查、检测库与候选结果 UI、中文路径处理、二进制/空文件和读取失败测试。
- **产出**：文件编码检查工具。
- **演示**：检查 UTF-8 BOM 文件、无 BOM UTF-8 文件、ASCII 文件和二进制文件；展示证据和不确定性。
- **验收**：① 确定性 BOM 识别正确；② 不确定样本不会强行给出高可信唯一结论；③ 原文件不被修改；④ 读取失败可诊断。
- **不做**：转码、修复、批量覆盖文件。
- **依赖**：M00；可复用 M02 中合适的编码能力但不强制耦合模块。关联需求：FUN-05、SHELL-05。

### M06 — Windows 屏幕拾色器可用

- **目标**：完成一个真实的平台能力功能，通过抽象层读取其他应用界面颜色。
- **开发内容**：拾色交互状态、Windows 屏幕像素读取适配、RGB/HEX/HSV 显示与复制、取消操作、DPI/屏幕坐标基础处理。
- **产出**：Windows 屏幕拾色工具；同一业务接口下的其他平台“不支持”实现/声明。
- **演示**：在另一应用中显示纯红色块，启动拾色并选取 → 显示 `#FF0000`、RGB `255,0,0` 和相应 HSV；重复一次并按 Esc 取消。
- **验收**：① 能读取其他普通应用的可见像素；② 表达格式转换符合约定；③ 可取消；④ Windows API 不直接进入通用工具算法；⑤ 无法读取时给出反馈。
- **不做**：图片编辑器、截图标注、跨应用调色板管理；Linux 真正取色放在后期能力评估。
- **依赖**：M00。关联需求：FUN-06、SHELL-05。

### B 阶段结束门

- [ ] 六个工具均有独立页面，并能解决至少一项真实开发问题。
- [ ] 各工具至少通过关键正确性和错误路径的最低测试。
- [ ] 工具之间没有明显业务代码耦合；新增工具主要通过注册接入。
- [ ] 作者已在真实开发工作中至少试用一轮，并记录不足和新增需求。

此时即可得到一个**可日常使用的 Windows 工具集**；不必等待完整 CI、安装包或 Linux 移植。

## 6. C 阶段：工程化完善

### M07 — 中英文、配置与日志体验完善

- **目标**：将“能用的工具集合”整理为可长期自用的桌面软件。
- **开发内容**：补齐中文/英文翻译资源及切换、语言保存；日志级别/过滤/必要的文件日志；基础用户配置存储；常见 DPI 和中文输入回归。
- **产出**：中英文可用、设置可保持、诊断能力完善的 Windows 应用。
- **演示**：中文 → 英文切换；重启后语言保持；制造一个可预期错误并在日志中定位；恢复默认设置。
- **验收**：① 六个工具关键 UI 文本能够中英切换；② 配置写在用户目录；③ 日志中没有默认保存敏感输入；④ 旧工具仍可使用。
- **不做**：几十种语言、复杂主题系统。关联需求：SHELL-03/04/06。

### M08 — 自动化测试与 Windows CI

- **目标**：建立可持续回归验证的工程基础。
- **开发内容**：补充单元测试、模块集成测试和错误路径；按模块组织 CTest；GitHub Actions 在 Windows 上自动配置、构建、执行测试；整理最简 GUI 冒烟脚本。
- **产出**：仓库每次提交都能够自动发现主要逻辑回归的流水线。
- **演示**：本地运行 CTest；提交一个正常改动显示 CI 通过；在测试分支中故意制造一个可恢复的失败并验证流水线显示失败（验证后撤销测试性故障）。
- **验收**：① 核心算法都有确定性测试；② CI 成功/失败反馈可见；③ 测试不用依赖显示器或人工点击；④ 有单独的人工 GUI 冒烟清单。
- **不做**：追求某个没有依据的覆盖率百分比、一次性写完复杂 GUI 录制回放。关联需求：ENG-02/03。

### M09 — Windows 安装包可交付

- **目标**：让非开发环境也能安装和运行程序。
- **开发内容**：CMake `install()` 资源布局、依赖 DLL/运行时检查、CPack + NSIS、安装和卸载验证。
- **产出**：可安装的 Windows 安装包。
- **演示**：在干净 Windows 虚拟机/电脑中运行安装包 → 打开 DevCaddy → 运行 JSON、编码、取色工具 → 卸载。
- **验收**：① 不依赖 Visual Studio 开发环境；② 安装后字体/语言/动态库资源齐全；③ 可卸载；④ 用户数据处理符合预定策略。
- **不做**：自动更新服务、商店上架、数字签名采购。关联需求：ENG-04。

### M10 — 第一个公开 Windows Release

- **目标**：完整走通个人开源项目的首次正式交付。
- **开发内容**：README、架构概要、构建/使用说明、许可证、第三方许可、版本号、变更记录、发布制品；检查仓库无敏感资料。
- **产出**：可从 GitHub 下载的版本化 Release 和可复现构建说明。
- **演示**：另一台机器从 Release 下载安装；开发者按 README 克隆项目、构建并测试。
- **验收**：① 仓库公开内容符合授权和隐私要求；② Release 与源码版本对应；③ 下载的安装包可用；④ 基础构建说明可以由陌生开发环境复现。
- **不做**：维护大型社区、插件市场、复杂发布渠道。关联需求：ENG-05。

## 7. D 阶段：跨平台验证

### M11 — Linux 核心库与测试通过

- **目标**：验证跨平台的核心逻辑与平台边界并非只停留在设计上。
- **开发内容**：Linux + GCC/Clang + CMake/Ninja 编译核心/工具算法库；替换 Windows 特定依赖；执行测试；记录环境问题。
- **产出**：Linux 核心模块构建与测试结果，跨平台问题清单。
- **演示**：在 Linux（优先实际麒麟环境）运行 CMake 构建和 CTest，核心测试通过。
- **验收**：① 通用核心不依赖 Win32 API；② UTF-8 和文件路径测试通过；③ 存在明确可复现的构建步骤。
- **不做**：此时强制所有 GUI 功能运行。关联需求：XPLAT-01。

### M12 — Linux GUI 版本能够运行

- **目标**：交付可实际启动和使用通用功能的 Linux 桌面版本。
- **开发内容**：SDL3/ImGui Linux 后端、运行资源与依赖路径、中文输入和窗口交互；对屏幕拾色等平台差异能力显式降级；可选尝试 Linux 安装包。
- **产出**：Linux 可运行的 DevCaddy GUI 程序。
- **演示**：在 Linux 启动 GUI，使用 JSON、字符串编码、UUID、哈希等通用工具，查看日志并切换语言。
- **验收**：① 程序可启动退出；② 通用功能及核心测试通过；③ 不支持的取色行为明确说明；④ 不影响已有 Windows 版本。
- **不做**：所有发行版同时支持、Wayland 全局拾色的通用保证。关联需求：XPLAT-02/03。

## 8. CMake 学习目标与里程碑对应

| 里程碑 | 重点实践 |
| --- | --- |
| M00 | `project`、`add_executable`、`add_library`、`target_link_libraries`、基本依赖、Ninja、CTest 起步 |
| M01–M04 | 多 target 组织、`PUBLIC/PRIVATE/INTERFACE`、第三方库集成、编译特性、模块单测 |
| M05–M06 | 平台条件编译、Unicode 文件路径、Windows 系统库链接、资源与接口边界 |
| M07 | 翻译/字体资源、`configure_file` 或版本信息、配置目录约定 |
| M08 | `CTest`、测试目标注册、Preset、Windows CI 构建 |
| M09 | `install(TARGETS/FILES/DIRECTORY)`、运行时依赖、CPack/NSIS |
| M10 | Release 产物与版本管理、干净构建与可复现性 |
| M11–M12 | Linux 工具链、平台依赖查找、运行资源部署、编译器差异与 CI 扩展 |

注意：学习点不等于硬性“必须使用某条 CMake 命令”。没有实际需求时，不应为练习特性制造复杂度。

## 9. 每次里程碑评审的记录模板

建议每次完结时记录以下简表，不必形成冗长会议材料：

```markdown
## 里程碑：Mxx — 名称

- 状态：未开始 / 开发中 / 待验收 / 已通过 / 暂停
- 目标：
- 对应需求：
- 本次完成内容：
- 运行产物及环境：
- 演示步骤与实际结果：
- 自动测试（命令、通过/失败数）：
- 已知问题（阻塞/非阻塞）：
- Git 提交或版本号：
- 验收结论：通过 / 有条件通过 / 不通过
- 下一步：
```

**验收判断**：

- **通过**：必需条件满足，非关键问题已记录。
- **有条件通过**：有明确的剩余小问题、负责人（本人）和后续处理节点，且不影响下一阶段正确性。
- **不通过**：可运行性、核心正确性或关键平台边界没有满足；保持在当前里程碑处理。
- **回退**：发现早期核心接口导致多个工具重复修改，优先回到相关架构边界调整，不继续堆叠新功能掩盖问题。

## 10. 优先级与变更控制

1. 当前里程碑期间，只处理交付该功能必需的设计与缺陷；额外工具放入候选需求清单。
2. 发现功能比预期复杂时，先寻找仍能满足最主要使用场景的最小切片；不要削弱正确性条件。
3. 发现某项工程化改造会阻碍功能交付时，可记录技术债并后置；但不能破坏“业务/GUI 分离、平台依赖隔离、基本自动测试”三条底线。
4. 若 M01–M06 的工具优先级因实际工作需要变化，允许调整顺序，不必修改功能需求的稳定 ID。
5. 当前计划**不设置具体工期**；先完成 M00/M01 后，用实际编码与验证耗时估计后续里程碑。

## 11. 最终交付判定

**第一阶段可自用**：M00–M06 完成，Windows 程序具备六个实用工具和最低测试基线。

**第一阶段可公开发布**：再完成 M07–M10，Windows 程序具备中英文、测试、安装包和 GitHub Release。

**后续跨平台交付**：完成 M11–M12，在实际 Linux 环境构建、运行并验证主要功能。

后续动态插件、Asio 全面任务系统、GUI 自动化等属于“有明确使用需求再开新里程碑”的候选项，不预先强制占用计划。
