# DevCaddy 个人开发需求清单

> 版本：v0.1（2026-11-14）  
> 状态：可作为初版开发基线；尚未冻结的技术细节以实际原型验证为准。  
> 配套文档：《DevCaddy 开发阶段与里程碑计划》。

## 0. 文档用途与管理约定

本文件回答**“项目最终需要做什么、各项需求达到什么程度”**，不负责安排具体开发顺序。开发顺序、里程碑演示及阶段验收由配套计划管理。

- `[ ]` 表示尚未验收；完成后改为 `[x]`，并记录对应的测试、演示或提交。
- 每项需求保留稳定 ID；增加或调整内容时尽量不改变已分配 ID。
- 优先级 `P0`：首个可运行程序必须具备；`P1`：Windows 核心功能阶段完成；`P2`：工程化完善；`P3`：跨平台或按实际需要演进。
- `P0`、`P1` 不代表第一天全部写完；具体里程碑参见第二份文档。
- 此项目是**个人自用、手写 C++ 代码的实践项目**；AI 主要承担需求梳理、设计评审、测试方案与代码审查。

## 1. 项目定位与边界

**产品名称**：DevCaddy。GitHub 仓库名暂记为 `desktop_dev_caddy`（命名格式尚可调整，不影响需求）。

**定位**：一个运行在本地桌面上的轻量、可扩展开发辅助工具集，为日常开发提供编码、摘要、取色、UUID、JSON 等高频小工具，补充现有 IDE、编辑器和命令行工具。

**开发环境与约束**：

- 主语言 C++17；使用 CMake 管理构建，Windows 首选 VS2022 + Ninja。
- GUI 采用 Dear ImGui；初版拟使用 SDL3 + OpenGL3 后端（在 M00 验证）。
- Windows 为第一交付平台；Linux（含麒麟）需要保留真实的移植可能性。
- 功能算法可使用成熟开源库；工具框架、模块组织与集成由作者自己编写或参照成熟设计。
- 有实际后台处理需求时优先考虑 Asio；不预先建设复杂调度框架。
- 主要界面语言为简体中文和英文；语言机制允许后续新增其他语言。
- 计划在 GitHub 开源，并最终提供可安装、可卸载的 Windows 安装包。

**项目成功标准**：

- [ ] 六项核心工具能在 Windows 桌面软件中被独立打开并实际使用。
- [ ] 新增工具不需要侵入已有工具算法代码；核心算法不依赖 GUI。
- [ ] 从仓库代码可以按文档构建并执行自动化测试。
- [ ] 可以在没有开发环境的 Windows 机器上安装、运行与卸载。
- [ ] 在后期通过真实 Linux 构建及运行验证跨平台边界。

**首版明确不做**：完整 IDE、文本编辑器、复杂密码学产品、云端账户/同步、插件市场、任意第三方 DLL 插件、自动更新服务、大规模批量处理、跨设备协同。

## 2. 核心功能需求（P1）

### FUN-01 JSON 格式化与单行化（对应 M01）

- [ ] 输入或粘贴 JSON 字符串。
- [ ] 点击“格式化”，输出易读的多行缩进 JSON。
- [ ] 点击“单行化”，移除不必要的空白和换行，输出一行**合法 JSON**。
- [ ] 非法 JSON 给出错误反馈，不能静默输出误导性结果。
- [ ] 支持复制处理结果。
- [ ] 不要求 JSON/YAML/XML 互转、JSONPath、Schema 或复杂树形编辑。

**约定**：单行化指 `minify`，不是加外层引号并转义为 C++ 字符串字面量。格式化/单行化应保持 JSON 数据语义；不要求字节完全往返一致（例如对象键顺序与数值显示细节需服从所用库的定义）。

**可验证场景**：输入多行 `{"name": "test", "enabled": true}`（实际带缩进与换行），单行化输出 `{"name":"test","enabled":true}`；反向格式化后可正确解析；非法尾逗号报错。

### FUN-02 字符串编码结果展示（对应 M02）

- [ ] 输入或粘贴一段 Unicode 文本。
- [ ] 展示不同目标字符编码对应的十六进制字节与字节数。
- [ ] 首批优先支持 UTF-8、UTF-16LE、UTF-16BE；结合 Windows/麒麟工作需要，建议支持 GBK/GB18030。
- [ ] 每种编码的结果可独立复制。
- [ ] 如果某编码无法表示某字符，应明确提示，不能悄悄替换成 `?`。
- [ ] 可选显示 Unicode 代码点，帮助分析字符编码问题。

**约定**：UTF-16LE/BE 默认显示**不含 BOM** 的编码正文；需要 BOM 时单独说明。此功能不猜测粘贴文本的原始编码，也不把原始十六进制字节反向解码作为首版必需功能。

**可验证场景**：输入 `中`，UTF-8 `E4 B8 AD`，UTF-16LE `2D 4E`，UTF-16BE `4E 2D`，GBK `D6 D0`；验证混合中英文、表情符号和无法编码字符。

### FUN-03 UUID 生成器（对应 M03）

- [ ] 生成符合标准格式的 UUID v4。
- [ ] 支持生成一个 UUID，提供复制操作。
- [ ] 可以批量生成指定数量的 UUID（以简单合理的数量限制防止误操作）。
- [ ] 选用合适的随机源或成熟库，不用普通非安全伪随机数随意拼接。
- [ ] UUID v7、排序、复杂校验放在后续按需扩展。

**可验证场景**：检查 36 字符标准格式、版本位和变体位；批量生成数量正确；重复生成做基础碰撞检查，但不把抽样“无碰撞”作为绝对唯一性证明。

### FUN-04 哈希摘要工具（对应 M04）

- [ ] 支持文本输入，计算 SHA-256；建议同时提供 MD5 用于非安全性校验兼容。
- [ ] 明确文本按 UTF-8 等约定转换为字节后再计算，结果以十六进制显示。
- [ ] 支持复制摘要。
- [ ] 根据实际需要支持文件摘要；实现时须分块读取，避免一次性将大文件载入内存。
- [ ] 输入错误或文件读取失败时给出明确反馈。

**术语与安全边界**：哈希/摘要不是“加密”，不可解密；MD5 不适合抗碰撞安全用途。本项目不承担密码保存、密钥管理、数字签名等工作。

**可验证场景**：空文本、`abc`、中文文本与标准摘要测试向量一致；文件摘要与可信命令行工具一致。

### FUN-05 文件可能编码格式检测（对应 M05）

- [ ] 用户选择本地文件，程序只读获取原始字节。
- [ ] 分析 BOM、UTF-8 合法性等确定性证据。
- [ ] 对无明确编码标记的文件展示可能编码候选与判断依据/不确定性。
- [ ] 候选范围按选用检测库能力确定，优先考虑 UTF-8、UTF-16LE/BE、GBK/GB18030。
- [ ] 空文件、ASCII、过短样本、混合编码与二进制内容应允许报告“无法确定”。
- [ ] 中文文件路径与文件读取失败要得到合理处理。
- [ ] **不修改、修复或转码原文件**。

**正确性边界**：编码猜测是启发式判断，不以“所有文件唯一识别准确”为验收条件；能说明不确定性比猜错后假装确定更重要。

**可验证场景**：UTF-8 BOM 文件有清晰证据；无 BOM UTF-8 返回合理候选；ASCII/空文件不被强制判定；二进制文件不误报为高可信普通文本。

### FUN-06 屏幕像素拾色器（对应 M06）

- [ ] Windows 下点击“开始拾色”，可选择本软件以外的**普通应用窗口中的可见屏幕像素**。
- [ ] 选取后展示颜色块和 HEX、RGB、HSV 表达形式。
- [ ] 结果可复制；可取消本次拾色。
- [ ] 处理 DPI 缩放、屏幕边界以及无法读取像素的场景。
- [ ] 屏幕颜色读取逻辑通过平台能力接口调用，工具业务代码不直接依赖 Win32 细节。
- [ ] Linux 屏幕拾色能力可后期实现；不可用时明确反馈。

**约定**：屏幕最终合成像素通常提供 RGB，不能从截图推断来源控件原本的透明度；若显示 RGBA，应标明 Alpha 按不透明处理。

**可验证场景**：从其他应用中的纯红色块拾取后显示 `#FF0000` / `RGB(255,0,0)` / `HSV(0°,100%,100%)`；按 Esc 取消后不改写原结果；双显示器/不同缩放环境纳入后续回归。

## 3. 最小应用与基础架构需求（P0）

### SHELL-01 桌面应用壳（M00）

- [ ] 能启动、退出、响应窗口关闭和基本交互。
- [ ] 提供工具导航区、主工作区和日志窗口。
- [ ] 核心工具模块可以通过导航打开，彼此不混杂。
- [ ] 中文显示与输入法在首个原型得到基本验证。

### SHELL-02 微内核式扩展边界（M00 开始、随 M01~M06 验证）

- [ ] 定义最小工具描述信息、注册/创建入口及基本生命周期。
- [ ] 首版采用**静态注册/编译期链接**；不要求运行时 DLL 插件加载。
- [ ] 将工具的 ImGui 视图层和可独立测试的算法层分开。
- [ ] 工具彼此不直接依赖，不因为增加一个工具而修改其他工具算法。
- [ ] 内核通过有限的日志、配置、国际化与平台服务接口向工具提供公共能力。

### SHELL-03 日志（M00 基础、M07 完善）

- [ ] 日志窗口能够显示运行消息与错误信息。
- [ ] 日志至少区分级别和工具来源。
- [ ] 不默认记录用户粘贴的原始文本、完整文件内容、令牌等敏感输入。
- [ ] 后期补充持久化、过滤、滚动与保留策略；后台线程不能直接操作 ImGui。

### SHELL-04 国际化（M00 机制、M07 完善）

- [ ] UI 可通过资源键获得显示文本，而不是把所有中文/英文硬编码在工具中。
- [ ] 首版应用基础界面可显示简体中文；实现中英切换与语言保存。
- [ ] 字体覆盖中文字符，验证 UTF-8、Windows 输入法和高 DPI 基础行为。
- [ ] 后期补齐语言资源、缺失键回退和全模块切换测试。

### SHELL-05 平台能力边界（M00/M06，Linux 后续）

- [ ] 抽象必要的文件选择、剪贴板、应用配置路径、屏幕取色能力。
- [ ] 不创建臃肿的全能平台接口；每个接口服务于已存在的功能。
- [ ] Windows 特定代码集中在适配层，其他模块不直接依赖其头文件和类型。
- [ ] Windows 中文路径正确处理；不得默认认为本地窄字符路径就是 UTF-8。

### SHELL-06 配置与基本体验（M07）

- [ ] 语言、基础设置和必要的窗口状态可保存并恢复。
- [ ] 设置保存在用户配置目录，不写入安装目录。
- [ ] 操作失败时在 UI 中有简明提示，详细原因可在日志查看。

## 4. 工程化需求（主要 P2）

### ENG-01 CMake 与依赖组织（P0 起，逐步深入）

- [ ] 使用 target-based CMake 组织程序、核心库和工具模块。
- [ ] 建立 Windows Debug/Release 可靠构建流程，可使用 CMakePresets.json。
- [ ] 依赖库来源和版本可追溯，避免混乱的系统全局路径依赖。
- [ ] 根据真实项目需要实践 `PUBLIC/PRIVATE/INTERFACE`、构建选项、平台条件、资源复制与安装规则。

### ENG-02 最低测试基线（P0/P1，同功能同步推进）

- [ ] 首版项目接入 CTest，有可自动运行的最小测试目标。
- [ ] 每增加一个纯逻辑工具，至少覆盖典型正确用例和一个边界/错误用例。
- [ ] 单元测试不需要启动 GUI；测试失败返回非零结果。
- [ ] 每个里程碑开发完成后可以运行对应的快速测试。

### ENG-03 完善自动化测试（P2/M08）

- [ ] 为各核心工具补齐代表性编码样本、标准摘要向量、非法 JSON、文件错误等回归测试。
- [ ] 对工具注册、日志、国际化回退和平台接口进行集成测试。
- [ ] 通过 CTest 统一执行、输出结果，并设置 Windows GitHub Actions 构建/测试。
- [ ] GUI 冒烟测试可以先有人工脚本；条件合适再接入 Dear ImGui Test Engine，并复核其许可证。

### ENG-04 Windows 安装与交付（P2/M09）

- [ ] 通过 CMake `install()` 组织可执行文件、运行库、字体、语言等资源。
- [ ] 通过 CPack/NSIS 生成 Windows 安装包。
- [ ] 在无开发环境的干净 Windows 系统中验证安装、运行和卸载。
- [ ] 卸载时不误删用户的非临时个人文件，处理好配置目录策略。

### ENG-05 GitHub 开源与发布（P0 起、M10 完整交付）

- [ ] 从第一阶段使用 Git，保留有意义的提交历史。
- [ ] 提供 README（定位、构建、使用说明）、LICENSE、第三方许可信息。
- [ ] 完成首个可下载的 Windows GitHub Release、版本号和变更记录。
- [ ] 避免提交公司专有代码、涉密数据、凭据或未获许可的第三方资产。

## 5. 跨平台与后续需求（P3）

- [ ] XPLAT-01：Linux 上可构建核心算法库并通过对应测试（M11）。
- [ ] XPLAT-02：Linux 上可以启动桌面 GUI、运行通用工具，资源路径和中文输入可用（M12）。
- [ ] XPLAT-03：对于 Linux/Wayland 无法实现的屏幕拾色能力，提供清晰的不可用提示；后续按需接入系统授权机制。
- [ ] EXT-01：确实出现可观测的 UI 卡顿时，加入后台任务、进度、取消及关闭时生命周期处理；优先考虑 Asio。
- [ ] EXT-02：确实需要独立分发第三方工具时，再研究动态插件、ABI、错误隔离与版本管理。
- [ ] EXT-03：按实际使用增加新工具，不为扩大工具数量而增加功能。

## 6. 非功能要求

| ID | 维度 | 基线要求 | 验证方法 |
| --- | --- | --- | --- |
| Q-01 | 正确性 | 编码、摘要、JSON、UUID 等算法输出与已知案例一致 | 单元测试/测试向量 |
| Q-02 | 稳定性 | 错误输入、文件读取失败不能导致进程崩溃 | 错误路径测试 |
| Q-03 | 响应性 | 日常短文本操作不明显阻塞；大文件不应无界占用内存 | 手工观测、分块读取/按需后台化 |
| Q-04 | 可维护性 | 业务逻辑不依赖 Dear ImGui，平台依赖集中在适配层 | 依赖关系审查、独立测试 |
| Q-05 | 可扩展性 | 增加新工具主要新增模块与注册代码，不改动其他工具算法 | 通过 M01/M02 连续接入验证 |
| Q-06 | 国际化 | 中英文本显示和输入正常，语言资源可继续扩展 | 手工语言切换与字体测试 |
| Q-07 | 隐私 | 默认离线本地运行，不主动上传用户输入与文件 | 功能与依赖行为审查 |
| Q-08 | 可复现 | 在明确文档和依赖条件下能重新构建 | 新环境/CI 构建 |

暂不指定启动时间、文件最大容量、测试覆盖率百分比等缺乏基线的数据；在真实原型运行后再设置有意义的定量要求。
